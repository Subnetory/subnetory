# Changelog

All notable changes to Subnetory will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project follows semantic versioning pragmatically during early development.

## [0.8.7] - 2026-08-04

### Fixed

* **Premier run du job CI `accessibility-smoke` en echec (05/08/2026)** : risque deja signale au moment d'introduire ce job (voir F-03 ci-dessous) — axe-core a releve une violation `color-contrast` sur le sous-titre de `/login` (`.sn-login-subtitle`, texte "Gestion d'adresses IP"). `--color-text-muted` (#9aa3b0) sur le fond blanc de la carte de connexion ne donne qu'un ratio ~2.55:1, sous le seuil WCAG 2 AA de 4.5:1 pour du texte de cette taille (13.2px, sous le seuil "grand texte"). Corrige en basculant cet element sur `--color-text-secondary` (#5a6475, ratio ~5.97:1), deja present dans la palette de couleurs — pas de nouvelle couleur introduite, changement cible sans impact sur les autres usages de `--color-text-muted`.
* **Régression `mvnw clean verify` sur les correctifs ci-dessous, trouvée par Nahim (04/08/2026)** : 127 tests en échec après le premier passage de ce lot. Deux causes distinctes, sans rapport avec la sécurité des correctifs eux-mêmes, uniquement des effets de bord sur les tests : (1) `RestoreMaintenanceFilter` (M-01 ci-dessous) interroge désormais `RestoreMaintenanceGate#tryAdmitMutation()` plutôt que l'ancien `isActive()` — sur un `@MockitoBean` non stubbé, une méthode booléenne non stubbée renvoie `false` par défaut, ce qui signifiait auparavant « pas de restauration en cours » (comportement correct) mais signifie désormais « mutation refusée » (503 systématique), cassant toute requête de mutation dans huit classes de test Web (`AddressCrudWebIT`, `AddressWebImportIT`, `AdminBackupWebControllerIT`, `AdminWebControllerIT`, `ContextCrudWebIT`, `SiteCrudWebIT`, `SubnetCrudWebIT`, `VlanCrudWebIT`) qui mockent ce bean sans le stubber, faute d'avoir besoin de tester son comportement. Stub explicite (`tryAdmitMutation()` → `true`) ajouté dans le `setUp()` de chacune. (2) La lecture bornée de la sonde `--version` (F-04 ci-dessous) partageait la même limite configurable que la sortie d'un scan/dump réel (`maxOutputBytes`) — un test réglant volontairement cette limite à quelques octets pour vérifier le comportement sur une sortie de scan trop volumineuse faisait par effet de bord échouer la sonde elle-même en premier (bannière de version « java --version » > quelques octets), masquant le scénario réellement testé. Nouveau champ dédié `probeMaxOutputBytes` (64 Ko fixes, indépendant de la limite configurable) dans `ScanService` et `BackupExecutionService`, découplant la sonde de disponibilité de la sortie réelle de l'outil. `AdminBackupWebControllerIT#roleBackup_dashboard_hidesAdminOnlyActions` corrigé au passage : l'assertion cherchait le mot « Restaurer » dans toute la page, qui apparaît aussi dans un texte d'aide statique toujours affiché — remplacée par une vérification précise du lien `restore-confirm`, avec un historique de sauvegarde non vide pour que le test exerce réellement le `sec:authorize` du template plutôt qu'un hasard de fixture vide.
* **`RestoreMaintenanceFilter` bloquait les nouvelles mutations sans drainer celles déjà admises (04/08/2026, correctif MOYEN, troisième audit externe 04/08/2026)** : le filtre rejetait bien toute nouvelle requête de mutation une fois le mode maintenance activé, mais une requête déjà en vol au moment de l'activation pouvait terminer son traitement et écrire en base après la fin de `pg_restore` — contrairement à ce que documentait le commentaire existant ("au pire ralentie"), il s'agit d'une véritable incohérence de données possible, pas seulement d'un ralentissement. Nouvelle barrière de drainage dans `RestoreMaintenanceGate` : un compteur de mutations en vol (`tryAdmitMutation`/`releaseMutation`, mutuellement exclusif avec `begin()` via un moniteur partagé, fermant la fenêtre de compétition entre l'admission et l'activation du mode maintenance) et une attente bornée `awaitDrain(Duration)` avant de lancer `pg_restore` (`subnetory.backup.restore-drain-timeout-seconds`, défaut 65s — au-delà, la restauration se poursuit quand même avec un avertissement journalisé plutôt que de bloquer indéfiniment sur une requête bloquée, ce qui serait lui-même un déni de service). Tests de concurrence ajoutés (`RestoreMaintenanceGateTest`, y compris un test à 50 threads sur l'exclusion mutuelle). Voir `backend/docs/RESTORE_OPERATIONS.md`.
* **`networkPolicy.ingressFrom` vide par défaut y compris en profil production (04/08/2026, correctif MOYEN, troisième audit externe 04/08/2026)** : `values-production.yaml` activait `networkPolicy.enabled` sans imposer `ingressFrom`, ce qui rend en pratique la règle Ingress générée équivalente à aucune règle du tout — tout pod du cluster peut joindre directement le port applicatif, contournant l'Ingress/TLS/WAF (pas l'authentification applicative elle-même). Le chart refuse désormais de rendre les manifests (`{{- fail ... }}`) si `ingress.enabled=true` et `networkPolicy.enabled=true` sans `ingressFrom` non vide, sauf opt-out explicite via le nouveau `networkPolicy.allowAllIngressSources: true` (documenté comme un choix conscient, pas un défaut). Tests statiques CI ajoutés (`ci.yml`, job `helm-static`). Voir `backend/docs/INSTALL_KUBERNETES.md`.
* **`ROLE_BACKUP` : l'UI n'alignait pas ce que le serveur interdisait déjà (04/08/2026, correctif FAIBLE, troisième audit externe 04/08/2026)** : `AdminBackupWebController` refusait déjà 403 côté serveur à `ROLE_BACKUP` sur la configuration, la purge, la suppression, l'import et la restauration (hérité des correctifs `v0.8.5`/`v0.8.6`), mais `admin/backup.html` continuait d'afficher ces formulaires et boutons à un compte `ROLE_BACKUP`, qui découvrait l'interdiction seulement après soumission. `AssignableRoles.java` et `API_FIRST_PARITY.md` documentaient également encore l'ancien périmètre plus large de ce rôle. Formulaires et liens désormais masqués côté UI (`sec:authorize="hasRole('ADMIN')"`) pour un compte `ROLE_BACKUP` ; documentation resynchronisée avec le périmètre réel. Test de régression ajouté (`AdminBackupWebControllerIT`, `roleBackup_dashboard_hidesAdminOnlyActions`).
* **Arrêt tardif des process Nmap/pg_dump/pg_restore en cas d'échec de lecture de la sortie (04/08/2026, correctif FAIBLE, troisième audit externe 04/08/2026)** : les lectures bornées de stdout/stderr (garde-fou `max-output-bytes` introduit en `v0.8.5`/`v0.8.6`) pouvaient échouer sans que le process externe associé ne soit interrompu immédiatement, laissant le process parent attendre son propre timeout plutôt que de le tuer dès la première erreur de lecture détectée ; la sonde de disponibilité des outils (`assertNmapAvailable`/`assertToolAvailable`) n'avait par ailleurs pas de temporisation effective pendant la consommation de sa propre sortie. `ScanService#executeNmap`/`assertNmapAvailable` et `BackupExecutionService#runProcess`/`assertToolAvailable` attachent désormais un `whenComplete` à leurs futures de lecture qui appelle `destroyForcibly()` immédiatement sur toute erreur, en plus du `waitFor(timeout)` déjà en place ; la sonde applique désormais le même schéma probe-bornée-puis-kill. Tests de régression ajoutés (`ScanServiceTest`, `BackupExecutionServiceTest`).
* **42 templates Thymeleaf déclaraient statiquement `lang="fr"` (04/08/2026, correctif FAIBLE, troisième audit externe 04/08/2026)** : constat exact au niveau du code source, mais sans effet sur les pages réellement servies — Thymeleaf `th:replace` remplace entièrement la balise `<html>` du template appelant par celle du layout, rendant ces attributs statiques inertes dans 41 cas sur 42 (le 42e étant une bibliothèque de fragments). Corrigé par hygiène et pour clore complètement le constat : les 42 occurrences utilisent désormais `th:lang="${#locale.language}"`, cohérent avec le layout principal. Nouveau job CI `accessibility-smoke` (`ci.yml`) : construit l'application via Docker Compose et exécute axe-core (`@axe-core/cli`, tags WCAG2 A/AA) contre `/login` — premier contrôle d'accessibilité automatisé du projet.

### Added

* **Provenance et intégrité de la chaîne de release (04/08/2026, correctif MOYEN, troisième audit externe 04/08/2026)** : la release publiait déjà un `SHA256SUMS.txt` (`v0.8.5`) mais aucun SBOM, aucune signature, aucune attestation de provenance. `backend/pom.xml` génère désormais un SBOM CycloneDX du JAR (`cyclonedx-maven-plugin`, `bom.json`, publié sous `subnetory-bom.json`) ; `docker/build-push-action` génère un SBOM natif et une attestation de provenance SLSA attachés directement à l'image GHCR (flags BuildKit `sbom`/`provenance`) ; l'image publiée et `SHA256SUMS.txt` sont signés en mode "keyless" avec Cosign via l'identité OIDC de ce workflow GitHub Actions (aucune clé privée générée, stockée ni à faire tourner). Voir la nouvelle section "Release integrity" de `SECURITY.md` pour les commandes de vérification (`cosign verify`, `cosign verify-blob`). **Reste hors périmètre de ce correctif** (accès réseau indisponible pour le résoudre au moment de la remédiation) : épinglage par digest des images de base `eclipse-temurin` dans `Dockerfile` et `distributionSha256Sum` dans `backend/.mvn/wrapper/maven-wrapper.properties` — à traiter dès que possible, voir `SECURITY.md`.
* **Analyse statique CodeQL bloquante sur le dépôt public (04/08/2026, correctif informationnel, troisième audit externe 04/08/2026)** : le job `codeql` (introduit en `v0.8.6`) restait non-bloquant (`continue-on-error: true`) sur tous les dépôts, un compromis délibéré pour le fork de développement interne (sans licence GitHub Code Security payante). Ce compromis n'a cependant aucune raison de s'appliquer au dépôt public, où GitHub Advanced Security est disponible gratuitement et où CodeQL fonctionne et téléverse déjà correctement. `continue-on-error` est désormais conditionné à `github.repository != 'Subnetory/subnetory'` : bloquant sur le dépôt public, toléré sur le fork interne.
* **Scan de secrets absent malgré un job `dependency-scan` déjà en place (04/08/2026, correctif P1, troisième audit externe 04/08/2026)** : Trivy tournait déjà en CI (`ci.yml`) et en tâche planifiée hebdomadaire (`scheduled-dependency-scan.yml`), mais sans le paramètre `scanners`, seul le scanner `vuln` s'exécute par défaut — aucune détection de secret accidentellement commité n'était réellement effectuée malgré le nom générique du job. `scanners: vuln,secret` ajouté aux quatre étapes Trivy concernées (scan du code source et de l'image Docker, dans les deux workflows).

## [0.8.6] - 2026-08-04

### Fixed

* **`ConcurrentSessionFilter` affichait un texte brut non traduit au lieu de rediriger vers `/login` (04/08/2026, trouve en test manuel post-restauration v0.8.5)** : apres qu'une restauration draine toutes les sessions Web (`SessionInvalidationService#expireAllSessions`), la requete suivante d'un onglet deja ouvert atteignait le `ConcurrentSessionFilter` de Spring Security sans `expiredUrl` configure — repli par defaut sur l'ecriture directe de son texte anglais non traduit dans la reponse, sans aucune navigation de retour vers l'application. `invalidSessionUrl` etait deja configure pour le cas (different) de session inconnue, mais `expiredUrl` de `maximumSessions()` ne l'a jamais ete ; l'ecart preexistant n'est devenu visible en pratique qu'une fois les restaurations testees en conditions reelles. Reutilise desormais la meme cible `/login?expired`. `backend/docs/RESTORE_OPERATIONS.md` documente egalement desormais qu'une restauration reinitialise l'integralite de la table des utilisateurs (mots de passe, MFA, roles, existence des comptes) et pas seulement les donnees metier.
* **`ForwardedHeaderFilter` neutralisait la verification `trusted-proxy-cidrs` (04/08/2026, correctif MOYEN, audit externe 04/08/2026)** : `server.forward-headers-strategy=framework` enregistrait l'auto-configuration Spring Boot standard de `ForwardedHeaderFilter`, qui reecrit `getRemoteAddr()`/`isSecure()` de maniere INCONDITIONNELLE, avant meme que `ClientIpResolver` ne s'execute — rendant sa verification `trusted-proxy-cidrs` inoperante face a un client atteignant directement le pod/conteneur (usurpation d'IP dans le journal d'audit, contournement du rate limiting). Nouveau `TrustAwareForwardedHeaderFilter` : applique la meme reecriture (delegue a une instance normale de `ForwardedHeaderFilter`), mais seulement pour les connexions dont l'adresse TCP directe correspond a `trusted-proxy-cidrs` (meme verification que `ClientIpResolver`, methode `isRequestFromTrustedProxy` desormais publique). `SERVER_FORWARD_HEADERS_STRATEGY=framework` retire de `charts/subnetory/templates/configmap.yaml` et `backend/docker-compose.https.yml` (le nouveau filtre ne depend d'aucune variable supplementaire). Nouveau champ Helm optionnel `networkPolicy.ingressFrom` pour restreindre en complement l'entree applicative au controleur Ingress (defaut inchange : ouvert a tout pod du cluster, le namespace/labels du controleur variant trop selon l'installation pour un defaut fiable). Tests ajoutes (`TrustAwareForwardedHeaderFilterTest`, `ClientIpResolverTest`), regression CI ajoutee (le rendu Ingress ne doit plus jamais contenir `SERVER_FORWARD_HEADERS_STRATEGY`).
* **Mode maintenance de restauration : exemptions d'authentification et angles morts hors HTTP (04/08/2026, correctif MOYEN, second audit externe 04/08/2026)** : `RestoreMaintenanceFilter` exemptait initialement `/api/v1/auth/token`, `/change-password-required`, `/logout`, `/logout-all` et `POST /login` au motif qu'ils "ne modifient aucune donnee metier" — or ils ecrivent bel et bien en base (journal d'audit d'authentification, MFA, compteur anti-bruteforce, mot de passe, jetons revoques). Ces exemptions sont retirees : aucune mutation HTTP n'est plus exemptee pendant une restauration. Deux angles morts distincts corriges en complement : (1) la chaine de securite dediee a la deconnexion API (`apiLogoutFilterChain`, `@Order(0)`) n'avait jamais ete raccordee au filtre, contrairement aux trois autres chaines ; (2) deux taches planifiees ecrivant en base (`AuthAuditRetentionScheduler`, `RevokedTokenPurgeScheduler`) n'etaient couvertes par aucun garde-fou, `RestoreMaintenanceFilter` ne s'appliquant qu'aux requetes HTTP — les deux verifient desormais `RestoreMaintenanceGate#isActive()` et s'auto-suspendent le temps d'une restauration (troisieme tache planifiee, `BackupSchedulerService`, deja protegee par `operationInProgress`). Un scan Nmap deja accepte avant le debut d'une restauration continuait par ailleurs de s'executer jusqu'a son terme puis d'ecrire ses resultats sans verification : `ScanService#scan` refuse desormais d'ecrire (nouveau `ScanException.Reason.RESTORE_IN_PROGRESS`, HTTP 503) si une restauration est active, verifie a la fois au tout debut (rejet immediat) et juste avant l'ecriture (couvre le demarrage d'une restauration pendant le scan). Limite connue et documentee, jugee disproportionnee a corriger vu la fenetre de risque residuelle tres etroite sur une application mono-instance : une requete de mutation deja acceptee juste avant l'activation du mode maintenance n'est ni interrompue ni "drainee", elle continue normalement (au pire ralentie par les verrous de la transaction `pg_restore --single-transaction`) — voir la javadoc de `RestoreMaintenanceFilter`. Tests de regression ajoutes (`RestoreMaintenanceFilterTest`, `AuthAuditRetentionSchedulerTest`, `RevokedTokenPurgeSchedulerTest`, `ScanServiceTest`). Voir `backend/docs/RESTORE_OPERATIONS.md`.
* **`ROLE_BACKUP` restait trop puissant apres le premier correctif (04/08/2026, correctif MOYEN, second audit externe 04/08/2026)** : le correctif precedent (v0.8.5) avait deja reserve import/restauration a `ROLE_ADMIN`, mais `ROLE_BACKUP` conservait la modification de la configuration de sauvegarde, la purge en masse et la suppression individuelle de l'historique — un compte `ROLE_BACKUP` compromis pouvait desactiver la sauvegarde planifiee, alterer sa retention/son cron, ou detruire l'integralite de l'historique et des fichiers `.dump` sur disque, sabotant silencieusement la capacite de reprise apres sinistre sans jamais toucher a la base applicative elle-meme. `PUT /api/v1/admin/backup` (configuration), `POST .../purge` et `DELETE .../runs/{id}` (IHM et API, y compris la page de confirmation de suppression) exigent desormais `ROLE_ADMIN` explicitement, meme mecanisme que le correctif import/restore precedent. `ROLE_BACKUP` conserve uniquement le strict necessaire pour un compte de service ou un operateur dedie : lecture de la configuration, declenchement manuel, consultation de l'historique et telechargement. Tests de regression ajoutes (`AdminBackupWebControllerIT`). Voir `backend/docs/ADMIN_GUIDE.md`, `backend/docs/DB_PASSWORD_ROTATION_FEASIBILITY.md`.
* **La sonde `nmap --version` contournait le controle de concurrence des scans (04/08/2026, correctif FAIBLE, second audit externe 04/08/2026)** : `ScanService#scan` appelait `assertNmapAvailable()` (qui lance un process OS `nmap --version` distinct) tout au debut, avant meme d'acquerir les quotas de concurrence par utilisateur et global. Un appelant deja au-dela de sa limite continuait donc de declencher ce process de sonde a chaque tentative, avant d'etre rejete — la sonde elle-meme n'etait jamais throttlee, affaiblissant partiellement l'objectif du garde-fou introduit en v0.8.5. `assertNmapAvailable()` est desormais appelee dans `executeNmapThrottled`, apres acquisition reussie des deux quotas (par utilisateur puis global) : un appelant au-dela de sa limite recoit `TOO_MANY_CONCURRENT_SCANS` sans qu'aucun process de sonde ne soit lance. Tests de regression ajoutes (`ScanServiceTest`, verifiant qu'un chemin `nmapPath` invalide n'entraine plus `TOOL_NOT_AVAILABLE` quand le quota est deja epuise).
* **Invalidation JWT et invalidation des sessions Web post-restauration non independantes (04/08/2026, correctif FAIBLE, second audit externe 04/08/2026)** : `BackupExecutionService#invalidateSessionsAndTokensAfterRestore` enveloppait `UserTokenInvalidationService#invalidateAllTokens` (JWT, en base) et `SessionInvalidationService#expireAllSessions` (sessions Web, en memoire) dans un seul bloc try/catch — un echec de la premiere empechait silencieusement toute tentative de la seconde, alors que les deux mecanismes sont totalement independants. Chaque appel dispose desormais de son propre try/catch : l'echec de l'un n'empeche plus jamais la tentative de l'autre. Tests de regression ajoutes (`BackupExecutionServiceTest`, invoquant la methode directement par reflection pour couvrir les trois combinaisons d'echec sans necessiter un `pg_restore` reel).
* **Sortie stdout/stderr de pg_dump/pg_restore sans limite (04/08/2026, correctif FAIBLE, second audit externe 04/08/2026)** : `BackupExecutionService#readAllBytesAsync` utilisait `stream.readAllBytes()` sans borne, meme constat que pour Nmap (corrige en v0.8.5, `ScanService#maxOutputBytes`). Le contenu du dump lui-meme ne transite jamais par ce canal (pg_dump ecrit directement sur disque via `--file=...`, pg_restore lit depuis un fichier) : seuls les messages de diagnostic y transitent, normalement tres en-deca de toute limite raisonnable — mais rien n'empechait un comportement inattendu de faire croitre sans borne la consommation memoire du process applicatif. Nouveau garde-fou `subnetory.backup.max-output-bytes` (defaut 10 Mo, meme valeur par defaut que pour Nmap), applique a la fois a `pg_dump`/`pg_restore` et a la validation `pg_restore --list` d'un import. Tests de regression ajoutes (`BackupExecutionServiceTest`).

### Added

* **Seuils JaCoCo par paquet + analyse statique CodeQL (04/08/2026, correctif qualite, second audit externe 04/08/2026)** : le seuil de couverture existant ne portait que sur le bundle global (`LINE >= 0.75`, `BRANCH >= 0.55`), pouvant masquer un paquet a fort enjeu securite mal couvert derriere une bonne moyenne d'ensemble. Nouveaux seuils `PACKAGE` dedies pour `dev.subnetory.backup` (`LINE >= 0.55`, baseline mesuree 58 % — le plus gros fichier du projet, `BackupExecutionService` a lui seul ~1575 lignes, voir backlog refactor), `dev.subnetory.scan` et `dev.subnetory.security` (`LINE >= 0.60` chacun, mesure reelle au-dessus, marge conservee) — seuils mesures sur la baseline 971 tests (`backend/pom.xml`). Nouveau job CI `codeql` (`.github/workflows/ci.yml`) : analyse statique du code source Java (CodeQL, requetes `security-extended`), complementaire au scan de dependances existant (`dependency-scan`, Trivy) qui ne couvre que les vulnerabilites connues des bibliotheques tierces, pas les defauts du code applicatif lui-meme. Integration native GitHub Actions (onglet Security), sans plugin Maven ni service tiers supplementaire a maintenir. Voir `SECURITY.md`.

V9" alors que le depot est a V21 — corrige avec un renvoi au repertoire des migrations plutot qu'un compte fige. ## [0.8.5] - 2026-08-04

### Fixed

* **Helm Ingress sans forward-headers/trusted-proxy (04/08/2026, correctif ELEVE, audit externe 04/08/2026)** : `ingress.enabled=true` ne positionnait ni `SERVER_FORWARD_HEADERS_STRATEGY=framework` ni `SUBNETORY_SECURITY_TRUSTED_PROXY`/`_CIDRS`, contrairement a l'overlay `docker-compose.https.yml`. Consequence : `forward-headers-strategy` restait a `none`, donc tous les utilisateurs derriere l'Ingress apparaissaient avec la meme IP (celle du controleur Ingress) — rate limiting API et verrouillage anti-bruteforce mutualises entre utilisateurs, cookie de session sans l'attribut `Secure` derriere une terminaison TLS sur l'Ingress. Nouveau champ obligatoire `ingress.trustedProxyCidrs` (le chart refuse de rendre les manifests s'il est vide quand `ingress.enabled=true`) ; ConfigMap positionne desormais les trois variables automatiquement. Tests statiques CI ajoutes (rendu refuse sans le champ ; rendu avec le champ verifie les trois variables). Voir `backend/docs/INSTALL_KUBERNETES.md`.
* **`ROLE_BACKUP` equivalent a un acces administrateur complet des donnees (04/08/2026, correctif ELEVE, audit externe 04/08/2026)** : import et restauration de sauvegarde restaient accessibles a `ROLE_BACKUP` (`AdminBackupController`/`AdminBackupWebController`), alors que `pg_restore --list` ne valide que le format du dump importe, jamais son contenu, et qu'une restauration ecrase l'integralite de la base. Un compte `ROLE_BACKUP` seul pouvait donc importer puis restaurer un dump modifiant utilisateurs, roles ou donnees metier. `POST .../import` et `POST .../restore` (IHM et API) exigent desormais `ROLE_ADMIN` explicitement (`@PreAuthorize("hasRole('ADMIN')")` au niveau methode, en plus de la regle `hasAnyRole('ADMIN', 'BACKUP')` au niveau classe/URL). `ROLE_BACKUP` conserve configuration, declenchement, historique, telechargement, purge et suppression. Tests de regression ajoutes (403 pour `ROLE_BACKUP` sur import/restore-confirm/restore). Voir `backend/docs/DB_PASSWORD_ROTATION_FEASIBILITY.md`, `backend/docs/ADMIN_GUIDE.md`.
* **Scans Nmap sans limite de concurrence ni de taille de sortie (04/08/2026, correctif FAIBLE/MOYEN, audit externe 04/08/2026)** : rien n'empechait de declencher un nombre illimite de scans Nmap simultanes (chacun un processus OS distinct consommant CPU/reseau), et `readAllBytes()` sur stdout/stderr n'imposait aucune limite de taille. Nouveau garde-fou `ScanService` : semaphore global (`subnetory.scan.max-concurrent`, defaut 3, rejet immediat 429 au-dela, pas de file d'attente) et limite par utilisateur (`subnetory.scan.max-concurrent-per-user`, defaut 1), plus une lecture bornee de la sortie Nmap (`subnetory.scan.max-output-bytes`, defaut 10 Mo). Nouveau `ScanException.Reason.TOO_MANY_CONCURRENT_SCANS` (HTTP 429). Tests de regression ajoutes (`ScanServiceTest`).
* **Canal lateral 404/409 entre contextes (04/08/2026, correctif FAIBLE, audit externe 04/08/2026)** : `SiteService#create` et `VlanService#create` verifiaient l'unicite du code/VID AVANT le controle d'acces au contexte/site parent — un utilisateur pouvait ainsi distinguer, pour un contexte/site hors de son perimetre, une valeur deja prise (409 Conflict, atteint avant le controle d'acces) d'une valeur libre (404, atteint apres), revelant l'existence de codes de site ou de VID en dehors de son perimetre. Le controle d'acces au parent (`NetworkContextService#getEntityById`/`SiteService#getEntityById`, qui refusent tous deux de maniere identique par 404 que la ressource soit inexistante ou inaccessible) est desormais toujours effectue avant la verification d'unicite. Tests de regression ajoutes (`SiteServiceTest`, `VlanServiceTest`).

Reproduit deux fois sur des runs distincts. Cette boucle tolère maintenant les erreurs transitoires comme elle tolère déjà un Job en cours, jusqu'à la même échéance ; seule une indisponibilité persistante jusqu'au délai fait désormais échouer le restore drill, avec un message dédié distinguant ce cas d'un échec réel de restauration. Ce script est également celui utilisé pour les restore drills réels en production, pas seulement en CI.

* Restore safety: confirmation by exact file name (never a single click), SHA-256 checksum verification, automatic safety backup before every restore, retention that purges files but never history.
* Helm chart: dedicated `backupApp` PVC/ConfigMap for the in-app engine, alongside the existing standalone CronJob mechanism (`backup`); the chart now rejects enabling both against the same database.
* Clickable, click-to-copy SHA-256 checksums and file names on the backup screens.
* Backup import (01/08/2026): upload an external `.dump` file (e.g. downloaded from another instance) via `POST /admin/backup/import` / `/api/v1/admin/backup/import`; format is validated with `pg_restore --list` before acceptance, then the file is restorable like any other backup with the same protections.
* Manual, explicit history purge (01/08/2026): `POST /admin/backup/purge` / `/api/v1/admin/backup/purge` permanently deletes backup/restore history (and files) strictly before a given date, while protecting any backup still referenced by a retained restore.
* Optional label/comment per backup run (01/08/2026), shown in the history and restore confirmation screens.
* Automatic reconciliation of orphaned "RUNNING" backup/restore rows on application startup (01/08/2026): an operation interrupted by a crash or restart is now marked FAILED instead of staying stuck forever.
* Copy-to-clipboard for full error messages in the backup/restore history tables.
* Single-row backup delete (01/08/2026): `DELETE /api/v1/admin/backup/runs/{id}` / "Supprimer" button per row in `/admin/backup`, finer-grained than the mass purge-before-date. Refused with `409` if the backup is still referenced by a retained restore, or still `RUNNING`.
* Cascade backup delete (01/08/2026): `GET /api/v1/admin/backup/runs/{id}/linked-restores` lists exactly which restores reference a backup (as source or pre-restore safety copy); `DELETE .../runs/{id}?cascade=true` deletes them along with the backup instead of refusing. The web confirmation page (`/admin/backup/runs/{id}/delete-confirm`) lists the linked restores before offering this explicitly, keeping the strict refusal as the default.
* `ROLE_BACKUP` (01/08/2026): new assignable role limited to `/admin/backup` and `/api/v1/admin/backup` (configuration, trigger, import, restore, history), without the rest of administration. Follow-up of the DB password rotation feasibility study (`backend/docs/DB_PASSWORD_ROTATION_FEASIBILITY.md`).
* Backup encryption at rest (01/08/2026, backlog #13; enabled by default since 01/08/2026 for new Docker Compose installs — see the breaking-change entry below): AES-256-GCM + a separate HMAC-SHA256 over the whole file (independent keys derived via PBKDF2WithHmacSHA256, per-file random salt), streamed on both write and read paths. Key comes exclusively from `SUBNETORY_BACKUP_ENCRYPTION_KEY` (Docker secret / Kubernetes Secret via the existing configtree mechanism, or a raw env var for dev) — never stored in the database, never settable from the UI, same reasoning as `DB_PASSWORD_ROTATION_FEASIBILITY.md`. Once configured, new backups (scheduled/manual/pre-restore safety) are encrypted transparently; restore decrypts to a temp file right before `pg_restore` and always deletes it afterward; import detects and validates an already-encrypted file, or encrypts a plaintext import on the fly if the key is configured. Existing plaintext backups keep working unmodified — encryption only ever applies going forward, never retroactively. New `backup_runs.encrypted` column, `encrypted`/`encryptionEnabled` fields in the API, badge in the history table. See `backend/docs/BACKUP_ENCRYPTION.md` for the on-disk format and the important caveat that changing/losing the key is not a rotation — it permanently locks out backups already encrypted with the old value.
* Visual cron builder on `/admin/backup` (01/08/2026): tabs for Daily/Weekly/Monthly/Interval/Custom above the existing cron text field, which stays the single source of truth submitted to the server (server-side validation unchanged, `BackupConfigurationService`/Spring `CronExpression`). Weekly lets you pick one or more days as highlighted chips; Interval covers "every N hours" and "every N days" (e.g. every other day) at a given time; the field is read-only outside Custom mode to avoid drift, and any existing expression the structured modes don't recognize exactly falls back to Custom with the raw text preserved. Pure front-end enhancement (`app.js`/`app.css`), no backend or data-model change.
* Audit log extended to the whole backup lifecycle and to network-resource CRUD (01/08/2026, backlog #27): every backup action now has its own event type — `BACKUP_TRIGGERED`, `BACKUP_IMPORTED`, `BACKUP_RESTORED`, `BACKUP_DELETED`, `BACKUP_PURGED`, `BACKUP_SETTINGS_UPDATED` — recorded by `BackupExecutionService`/`BackupConfigurationService` with the acting username (from `SecurityContextHolder`), so it's now possible to answer "who ran/deleted/restored/purged which backup, and when" from `/admin/audit-log` alone, instead of only the file timestamps. Creating or deleting an IP address, VLAN, context, site or subnet is now audited too (`ADDRESS_CREATED`/`_DELETED`, `VLAN_CREATED`/`_DELETED`, `CONTEXT_CREATED`/`_DELETED`, `SITE_CREATED`/`_DELETED`, `SUBNET_CREATED`/`_DELETED`), on both the REST API and the web controllers, with a human-readable target (IP address, `VLAN <vid> (<name>)`, name, or CIDR). No schema change: the 16 new event types reuse the existing `auth_audit_log` table and its free-text `message` column. The audit-log filter dropdown and CSV export now group all 30 event types by category (Authentification/comptes, Sauvegardes, Ressources réseau).
* Manual audit-log purge (01/08/2026, backlog #27): `/admin/audit-log` gains a "Rétention" card showing the automatic nightly retention window (`subnetory.audit.retention.days`, 90 by default) and a form to purge entries strictly before a chosen date immediately, without waiting for the next scheduled run — `POST /admin/audit-log/purge` (web) / `POST /api/v1/admin/audit-log/purge` (API), both delegating to the existing `AuthAuditRetentionService` so the deletion logic itself is unchanged, only newly exposed and manually triggerable.

### Fixed

* Restore crash (`StaleObjectStateException`, 31/07/2026): `pg_dump` no longer includes the application's own backup metadata tables/sequences, which previously caused a 500 on restore and permanently stuck "RUNNING" rows in restored dumps.
* `pg_restore` now runs with `--exit-on-error` (01/08/2026): previously, a failed restore (e.g. blocked `DROP SEQUENCE`) could still silently execute later statements in the same archive, desynchronizing a sequence and causing a delayed `ConstraintViolationException` on the next backup.
* Double confirmation dialog on delete actions (01/08/2026): `app.js` had two independent `data-confirm` handlers — one on `click`, a duplicate one on `submit` — both firing for the same form, so every delete (addresses, contexts, sites, subnets, VLANs) required confirming twice. Removed the redundant handler.
* `.sn-chip-checkbox` not highlighting on click (01/08/2026): the CSS relied on `input:checked + .sn-chip-checkbox__pill` (immediate-sibling combinator), but on any checkbox bound with `th:field`, Thymeleaf injects a hidden `<input name="_xxx">` right after it for Spring's unchecked-checkbox binding, breaking that adjacency. Affected "Compte actif" (users), "Activer" (backup, LDAP), "Supprimer le mot de passe enregistré" (LDAP) and "IP temporaire" (address form). Switched to the `~` (general sibling) combinator; also added the missing `position: relative` on `.sn-chip-checkbox` so the visually-hidden input stays anchored to its label. Role/context chip lists were unaffected (bound via `name`/`th:value`/`th:checked`, not `th:field`). Table-row checkboxes (`.sn-table-checkbox`, bulk IP reservation) were also unaffected — styled directly on `:checked`, no sibling dependency.

### Changed

* **BREAKING for existing Docker Compose instances** — Backup encryption at rest enabled by default (01/08/2026, backlog #13): `backend/docker-compose.yml` and `backend/docker-compose.prod.yml` now declare the `subnetory_backup_encryption_key` secret unconditionally (previously commented out / opt-in), and `scripts/init-compose.ps1` / `scripts/init-compose.sh` now generate it by default alongside the three existing secrets. On an **existing** deployment where `backend/secrets/subnetory_backup_encryption_key` does not yet exist, `docker compose up` will fail with a missing-secret error until that file is created. Migration for an existing instance: re-run `pwsh -File .\scripts\init-compose.ps1` (or `./scripts/init-compose.sh`) **without** `-Force`/`--force` — thanks to the script's existing "only create missing secrets" behavior, only `subnetory_backup_encryption_key` is created; the JWT secret, admin password and PostgreSQL password already on disk are left strictly untouched — then `docker compose up -d --build` to reload the configuration. To opt out entirely, pass `-WithoutBackupEncryption` / `--without-backup-encryption` when (re)running the script and keep the corresponding secret blocks commented out in the Compose file(s) in use. See `backend/docs/BACKUP_ENCRYPTION.md` and `backend/docs/INSTALL_DOCKER_COMPOSE.md` for details. The Kubernetes Helm chart is unaffected: backup encryption remains unwired there (pre-existing gap, out of scope for this change).
