Utilisateurs, rôles & MFA

Gestion des comptes, rôles disponibles, révocation de jetons et récupération d'urgence.

Rôles disponibles

RôleDroits
ROLE_ADMINAccès complet, gestion des utilisateurs et de l'administration
ROLE_READ_ONLYConsultation des données des contextes autorisés
ROLE_NETWORKCréation et modification des contextes, sites, VLAN, sous-réseaux et scans
ROLE_IPCréation, modification, suppression, import et export d'adresses IP
ROLE_BACKUPAccès limité à /admin/backup (configuration, déclenchement, import, restauration, historique) — sans le reste de l'administration

Les rôles peuvent être cumulés : un utilisateur ROLE_NETWORK + ROLE_IP administre l'exploitation réseau et les adresses IP sans accès à l'administration de l'application. Pour un compte d'automatisation en lecture seule, attribuer ROLE_READ_ONLY et limiter son périmètre aux contextes nécessaires. ROLE_BACKUP convient à un compte de service ou un opérateur dédié aux sauvegardes.

Gestion des comptes

Menu Administration → Comptes (/admin/users). Chaque compte local est créé avec un mot de passe temporaire ; l'utilisateur est contraint de le changer à la première connexion (mustChangePassword) avant de pouvoir utiliser l'application ou obtenir un jeton API. Un administrateur peut réinitialiser le mot de passe d'un compte local depuis l'écran de détail utilisateur — cela réactive aussi la contrainte de changement obligatoire.

Depuis la même fiche, un compte peut être désactivé (réversible : l'accès est bloqué mais le compte et son historique restent consultables) ou supprimé définitivement (section « Zone dangereuse », irréversible). La suppression est refusée pour son propre compte et pour le dernier compte ROLE_ADMIN actif. Le journal d'audit et l'historique des sauvegardes ne sont pas affectés par une suppression : privilégier la désactivation si la fiche du compte doit rester consultable.

Révocation des jetons API

Depuis l'écran de détail d'un utilisateur, l'action Invalider les jetons invalide globalement tous les jetons JWT API déjà émis pour ce compte — les nouveaux jetons émis après l'action restent valides. Ce mécanisme se déclenche aussi automatiquement lors d'un changement de mot de passe ou d'une réinitialisation administrative, pour éviter qu'un ancien jeton reste utilisable après une modification sensible.

Cette invalidation ne concerne que les jetons API JWT. Elle ne déconnecte pas les sessions Web déjà ouvertes.

Authentification à deux facteurs (MFA) — vue administrateur

Chaque compte local peut activer le MFA depuis son propre profil (voir le guide utilisateur). Les comptes LDAP ne sont pas concernés.

Récupération en cas de perte du mot de passe ET du MFA

Si un compte perd l'accès à son mot de passe et à son application d'authentification (et que les codes de récupération n'ont pas été conservés), aucune récupération en libre-service n'est possible : Subnetory n'envoie pas d'email et ne propose pas de lien de réinitialisation par courrier électronique.

Si un autre compte ROLE_ADMIN existe, c'est la voie normale de récupération, entièrement depuis l'interface : depuis /admin/users, ouvrir la fiche du compte bloqué et réinitialiser son mot de passe. Cela ne désactive pas le MFA.

Sur cette même fiche (/admin/users/{id}), section MFA, le bouton « Désactiver le MFA » retire le second facteur du compte sans toucher au mot de passe — action anti-lockout prévue précisément pour ce cas. Réinitialiser le mot de passe puis désactiver le MFA suffit donc à débloquer entièrement le compte, sans aucune intervention en base de données.

Seulement si aucun autre compte admin n'existe, le recours devient un accès direct à la base PostgreSQL — procédure de secours à n'utiliser qu'en dernier ressort, par une personne de confiance ayant accès au serveur. Détail complet (requêtes SQL, génération du hash bcrypt) dans backend/docs/ADMIN_GUIDE.md, section « Authentification à deux facteurs (MFA) ».

Bonne pratique : maintenir au moins deux comptes ROLE_ADMIN actifs, pour ne jamais dépendre d'un compte unique.

LDAP

Menu Administration → LDAP (/admin/ldap) : configuration de l'annuaire, filtre de recherche utilisateur, rôles par défaut attribués à l'auto-provisionnement, et diagnostic de connexion.
