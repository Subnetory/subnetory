Sauvegarde & restauration

Deux mécanismes indépendants existent — ne pas les activer ensemble sur la même base.

Moteur intégré (recommandé)

pg_dump/pg_restore lancés par l'application elle-même, identique en Docker Compose et Kubernetes. Interface : /admin/backup. API REST complète, parité totale avec l'interface, préfixe /api/v1/admin/backup, réservée à ROLE_ADMIN ou ROLE_BACKUP (jeton Bearer requis).

Toute sauvegarde ou restauration restée « En cours » suite à un arrêt brutal (rebuild, crash) est automatiquement marquée en échec au démarrage suivant — aucune ligne ne reste bloquée indéfiniment.

Actions disponibles depuis /admin/backup

  • Planification automatique via un configurateur cron visuel (quotidien, hebdomadaire, mensuel, intervalle ou expression personnalisée).
  • Déclenchement manuel immédiat, avec titre/commentaire optionnel.
  • Téléchargement d'un fichier de sauvegarde, avec empreinte SHA-256 vérifiable.
  • Import d'un fichier .dump externe (vérifié via pg_restore --list avant acceptation), restaurable ensuite comme n'importe quelle autre sauvegarde.
  • Restauration avec confirmation par saisie exacte du nom de fichier — jamais en un clic — et sauvegarde de sécurité automatique juste avant.
  • Suppression fine d'une sauvegarde, ou en cascade avec ses restaurations liées.
  • Purge manuelle de l'historique avant une date donnée.

Chiffrement au repos (optionnel)

Désactivé par défaut. Une fois activé : AES-256-GCM + HMAC-SHA256, clé dérivée par PBKDF2 à partir d'une passphrase fournie exclusivement via la variable SUBNETORY_BACKUP_ENCRYPTION_KEY — jamais stockée en base, jamais modifiable depuis l'interface.

Une fois configurée, toute nouvelle sauvegarde (planifiée, manuelle, ou de sécurité pré-restauration) est chiffrée automatiquement (badge « Chiffré » dans l'historique, champ encrypted dans l'API). Les sauvegardes existantes non chiffrées restent utilisables normalement — le chiffrement ne s'applique jamais rétroactivement.

Ce n'est pas une rotation de clé. Changer ou perdre la valeur de la clé rend définitivement illisibles toutes les sauvegardes déjà chiffrées avec l'ancienne valeur. Conservez la passphrase en dehors de l'application (gestionnaire de secrets de l'équipe), au même titre que le mot de passe PostgreSQL, et ne la changez jamais une fois des sauvegardes chiffrées produites.

Génération et protection du secret (permissions restrictives Windows/Linux), et procédure pour une nouvelle instance qui doit rester capable de lire des sauvegardes chiffrées par une autre instance : voir backend/docs/BACKUP_ENCRYPTION.md et backend/docs/INSTALL_DOCKER_COMPOSE.md.

Commandes API

Configuration et état courant GET /api/v1/admin/backup
Déclencher une sauvegarde immédiate curl -s -X POST /api/v1/admin/backup/trigger -H "Authorization: Bearer <token>" -H "Content-Type: application/json" -d '{"label":"avant migration"}'
Restaurer (confirmation par nom exact de fichier) curl -s -X POST /api/v1/admin/backup/restore -H "Authorization: Bearer <token>" -H "Content-Type: application/json" -d '{"backupRunId":42,"confirmationText":"subnetory-20260731-020000.dump"}'
Purger l'historique avant une date curl -s -X POST /api/v1/admin/backup/purge -H "Authorization: Bearer <token>" -H "Content-Type: application/json" -d '{"beforeDate":"2026-01-01"}'

Référence complète des endpoints (schémas de requête/réponse) : Swagger UI /swagger-ui.html. Voir aussi le guide API.

Indépendants de l'application, utiles en secours si celle-ci est indisponible. Windows + Docker Desktop uniquement.

Détail complet (paramètres, automatisation via le Planificateur de tâches Windows, procédure de restauration d'urgence pas à pas) : backend/docs/BACKUP_STRATEGY.md, backend/docs/RESTORE_OPERATIONS.md, backend/docs/BACKUP_SCHEDULING_WINDOWS.md.

Règles de sécurité pour toute restauration

  • Ne jamais restaurer sans avoir vérifié le chemin complet et la date du fichier.
  • Ne jamais lancer une restauration production sans sauvegarde de sécurité préalable et fenêtre d'intervention identifiée.
  • Après restauration : vérifier le démarrage de l'application, l'authentification, la cohérence des données et l'absence d'erreur dans les journaux.
  • Documenter toute restauration (date, environnement, fichier utilisé, résultat) dans un compte rendu d'intervention.
