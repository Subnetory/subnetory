Déploiement Kubernetes

Chart Helm mono-réplique, avec PostgreSQL inclus ou externe.

Périmètre

Le chart charts/subnetory impose replicaCount: 1. Il ne fournit ni haute disponibilité applicative, ni opérateur PostgreSQL, ni image publique officielle — l'image doit être construite et rendue accessible aux nœuds du cluster.

Fournir l'image

Cluster kind (build local) docker build --tag subnetory:0.7.0 .\backend
kind load docker-image subnetory:0.7.0 --name NOM_DU_CLUSTER

Pour un autre cluster : construire l'image, la publier dans le registre privé autorisé, puis fournir image.repository/image.tag et image.imagePullSecrets dans les valeurs. Ne jamais utiliser un tag flottant comme latest.

Secrets Kubernetes

Comme pour Docker Compose, un script dédié crée les Secrets sans jamais afficher leur valeur, et refuse d'écraser un Secret existant :

PowerShell kubectl create namespace subnetory
pwsh -NoProfile -File .\scripts\init-helm-secrets.ps1 -Namespace subnetory

Deux objets sont créés : subnetory-runtime-secrets (secret JWT, mot de passe PostgreSQL) et subnetory-bootstrap-secrets (mot de passe administrateur temporaire). Le chart ne génère aucun Secret et n'accepte aucune valeur secrète en clair dans values.yaml.

Installer avec PostgreSQL inclus

Valider puis installer helm lint .\charts\subnetory --strict
helm upgrade --install subnetory .\charts\subnetory --namespace subnetory --wait --timeout 10m

Crée un Deployment applicatif (stratégie Recreate), un Service ClusterIP, un StatefulSet PostgreSQL, et un PVC PostgreSQL de 8 Gi par défaut (ajustable via postgresql.persistence).

Installer avec PostgreSQL externe

Le rôle et la base externes doivent déjà exister. La valeur postgres-password du Secret runtime doit correspondre exactement au mot de passe du rôle externe configuré.

values non sensibles postgresql:
  enabled: false
externalDatabase:
  enabled: true
  host: postgresql.example.internal
  port: 5432
  database: subnetory
  username: subnetory
  sslMode: require

Sauvegardes planifiées (optionnel)

Désactivées par défaut, réservées au PostgreSQL inclus (le chart refuse leur activation avec une base externe). CronJobs par palier (hourly/daily/monthly/quarterly), chacun avec sa propre rétention. Une NetworkPolicy dédiée aux pods de sauvegarde refuse les entrées et limite les sorties au PostgreSQL inclus et au DNS du cluster.

Combiner ces sauvegardes planifiées (backup.enabled) avec le moteur intégré applicatif (backupApp.enabled) sur la même base est explicitement rejeté par le chart au rendu (helm template échoue volontairement).

Toujours valider le rendu avant activation : helm lint .\charts\subnetory --strict.
